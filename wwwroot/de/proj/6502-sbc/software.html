Übersicht

Die Software hat in diesem Projekt genau eine Aufgabe: beweisen, dass die Hardware funktioniert. Geschrieben ist sie in reinem 65C02-Assembler, ein kleines Programm pro Chip, dazu eine finale Demo. Hier geht es um die Toolchain, die Speicherkonfiguration, die Bibliotheken und die Programme, und zwischendurch auch um ein paar 6502-Grundlagen, damit man dem Code folgen kann.

Toolchain

Der Weg vom Quelltext ins EEPROM sieht so aus: In VS Code mit einer cc65-Erweiterung für das Syntax-Highlighting schreiben, mit ca65 assemblieren, mit ld65 und einer eigenen Speicherkonfiguration zu einem 32kB großen rom.bin linken, und das dann mit dem TL866A-Programmer und dem Open-Source-Tool minipro ins EEPROM schreiben. Das EEPROM wandert danach in den ZIF-Sockel auf der Platine.

Einen C-Compiler zu schreiben oder zu benutzen war laut Pflichtenheft ausdrücklich nicht Teil des Projekts. Die cc65-Suite könnte aber auch C für diese Platine übersetzen, die passende Speicherkonfiguration gibt es ja schon.

Das Build-Skript

Jedes Projekt hat ein kleines Bash-Skript compile.bash. Dateinamen braucht es keine: Es assembliert einfach jede .s-Datei im Ordner source/, linkt alle Objektdateien und flasht auf Wunsch gleich das ROM:

./compile.bash        # assemblieren + linken → output/rom.bin
./compile.bash -d     # … und das ROM-Image als Hexdump anzeigen
./compile.bash -f     # … und per minipro ins AT28C256 schreiben

Im Kern passiert dabei nicht viel mehr als das hier:

ca65 --cpu 65c02 $file -o ../output/$file.o -l ../output/$file.list -I ../../lib
ld65 -C ../memory_pcb.cfg -m main.map $OBJECTS -o rom.bin
minipro -p AT28C256 -w rom.bin

Jedes Projekt bringt zwei Linker-Konfigurationen mit: memory_pcb.cfg für die Platine und memory_breadboard.cfg mit der alten Adressbelegung vom Steckbrett.

Die Linker-Konfiguration

In memory_pcb.cfg steckt die komplette Speicherkarte der Platine. Ein paar Kniffe darin haben sich richtig bewährt:

  • Jeder Peripheriechip ist ein eigener MEMORY-Bereich mit define=yes. Der Linker exportiert dann Symbole wie __VIA1_START__, und die Bibliotheken berechnen ihre Registeradressen daraus (PORTB1 = __VIA1_START__ + 0). Zieht ein Chip um, ändert sich eine Zeile in der Konfiguration, nicht der Code.
  • 32 Segmente BANK0 bis BANK31 liegen alle auf demselben Bereich $0000–$3FFF, eins pro RAM-Bank.
  • ZEROPAGE liegt bei $0000, der Stack bei $0100 und BSS im gemeinsamen RAM.
  • CODE, ISRS und RODATA liegen im ROM, die VECTORS bei $FFFA–$FFFF.
  • Ungenutztes ROM wird mit $DB aufgefüllt, dem Opcode für STP. Springt die CPU aus Versehen ins Leere, bleibt sie einfach stehen, statt Datenmüll auszuführen. Auf dem Steckbrett war es noch $EA, also NOP.
  • In den Kommentaren ist auch die Interrupt-Zuordnung dokumentiert: ACIA1 auf IRQ0, ACIA2 auf IRQ1, GPU auf IRQ2, IO9 bis IOD auf IRQ3 bis IRQ7 und VIA3 auf NMI.

Auf dieser Platine liegen Zero Page und Stack im RAM mit Bänken. Deshalb fängt jedes Programm so an:

RESET:
    ldx #$FF        ; Stackpointer initialisieren
    txs
    lda #$FF        ; VIA1 Port B = Ausgang (Bankleitungen)
    sta DDRB1
    lda #$00        ; Bank 0 wählen
    sta PORTB1
    ; erst ab hier ist JSR sicher, vorher könnte der Stack die Bank wechseln

Das erste echte Programm

Funktioniert das RAM? Viel einfacher als so kann ein Test kaum aussehen:

loop:
    lda #$55        ; 01010101
    sta $4000       ; ins RAM schreiben
    lda #$AA        ; 10101010
    sta $4001
    nop
    lda $4000       ; zurücklesen
    lda $4001
    nop
    jmp loop

Und so sieht das im Logikanalysator aus:

8005  8D    R     sta abs
8006  00    R       Low-Byte
8007  40    R       High-Byte
4000  55    W     ← ins RAM geschrieben
…
4000  55    R     ← aus dem RAM zurückgelesen

Taster abfragen: 6502 gegen 65C02

Hier sieht man schön, was die Zusatzbefehle des 65C02 bringen. Klassisch braucht man drei Befehle pro Bit, mit BBR („branch if bit reset“) nur noch einen. Der Haken: BBR geht nur auf die Zero Page, deshalb wird der Port vorher dorthin kopiert.

; klassischer 6502: 3 Befehle pro Bit
    lda #$01
    bit PORTB2
    beq taster1

; 65C02: 1 Befehl pro Bit (nur Zero Page)
    lda PORTB2
    sta $03
    bbr0 $03, Taster_1   ; springen, wenn Bit 0 = 0 (Taster gedrückt)
    bbr1 $03, Taster_2
    ; … bis bbr7

Hello World auf dem LCD

    jsr lcd_setup
    ldx #0
HW: lda hello_world,x
    beq NEXT            ; Null-Terminator
    jsr print_char
    inx
    jmp HW
NEXT:
    lda #40             ; Cursor in Zeile 2
    jsr set_cursor
    ; … " 6502 is alive! " ausgeben

alive:       .asciiz " 6502 is alive! "

Ein falscher Interrupt

Mit diesen paar Zeilen habe ich den hartnäckigsten Fehler des Projekts eingekreist. Das Programm legt eine Rücksprungadresse und das Statusregister auf den Stack und tut dann so, als käme es aus einem Interrupt zurück. Eigentlich sollte die CPU danach bei $8000 neu anfangen. Was stattdessen passiert ist, steht bei der Inbetriebnahme.

    lda #$80    ; Rücksprungadresse High-Byte
    pha
    lda #$00    ; Rücksprungadresse Low-Byte
    pha
    php         ; Statusregister
    rti         ; "zurück" → sollte bei $8000 neu starten

Die finale Demo

Die finale Software läuft mit vollen 1MHz, weil bei langsamem Takt die seriellen Puffer überlaufen würden. Der Logikanalysator bleibt dafür draußen. Nach dem Reset werden Stack und Bank 0 eingerichtet, dann PIA, VIA2 mit CA1-Interrupt, LCD und beide ACIAs initialisiert, und mit CLI geht es los:

  • Taster → LEDs: Die Hauptschleife liest die Taster an VIA2 Port B, invertiert sie und schreibt sie auf PIA Port B. Alle gedrückten Taster sind also gleichzeitig zu sehen.
  • ACIA1 → LCD: Jedes empfangene Zeichen erscheint auf dem LCD und geht als Echo zurück. Man tippt am PC und liest auf der Platine.
  • ACIA2 → LEDs: Jedes empfangene Byte erscheint binär auf PIA Port A und geht ebenfalls als Echo zurück.
  • Der serielle Empfang läuft komplett interruptgesteuert über den Interrupt-Controller VIA2.

Die Interrupt-Routine dazu ist angenehm kurz. Das Lesen von Port A verrät die Quelle und löscht gleichzeitig das CA1-Flag:

ISR:
    sei
    pha
    lda PORTA2          ; welche Quelle? (löscht auch das CA1-Flag)
    sta $03
    bbr0 $03, COM1      ; IRQ von ACIA1 aktiv (low)
    bbr1 $03, COM2      ; IRQ von ACIA2 aktiv (low)
    jmp RETURN_IRQ
COM1:
    lda RXDATA1
    sta $20
    jsr print_char      ; aufs LCD
    lda $20
    jsr ACIA1_TRANSMIT  ; Echo
    jmp RETURN_IRQ
COM2:
    lda RXDATA2
    sta PORTA_PIA       ; auf die LEDs
    jsr ACIA2_TRANSMIT  ; Echo
RETURN_IRQ:
    pla
    cli
    rti

Firmware des Logikanalysators

Der Logikanalysator ist ein kleiner Arduino-Sketch für den BluePill. Die 16 Adress- und 8 Datenpins sowie CLK und R/W sind Eingänge. Per attachInterrupt wird bei jeder steigenden Taktflanke eine Routine aufgerufen, die alle Leitungen einliest und als eine Zeile ausgibt: erst die Adressbits, dann die Datenbits und am Ende Adresse, Richtung und Daten in Hex.

In der Pinliste sieht man übrigens noch die Narbe aus der Inbetriebnahme: A7 und A8 liegen inzwischen auf PC15/PC14 statt auf den USB-Pins PA11/PA12. Wie es dazu kam, steht bei der Inbetriebnahme.
